# แผนพัฒนาส่วนของแอดมิน

แบบหน้าจอ: [Figma – Internship Work Log – Admin](https://www.figma.com/design/FBxBsGMtUWfOq26OcyK4v3) (ยืนยันแบบแล้ว 27 พ.ย. 2569)
กติกาอ้างอิง [business-rules.md](business-rules.md) และสัญญา API [api-contract.md](api-contract.md)

ทุกโมดูลทำแบบเดียวกับหน้าของนักศึกษาและพี่เลี้ยง:
หน้าจอเรียกผ่าน `Api` เท่านั้น มีทั้งข้อมูลจำลองและ REST มีสถานะโหลด ผิดพลาด และว่าง
แจ้งผลด้วยข้อความมุมจอ และทำตาม [design-pattern.md](design-pattern.md)

| 2 | ผู้ใช้งาน และการตั้งรหัสครั้งแรก | L | 0 | รายชื่อพี่เลี้ยงใช้ต่อในโมดูล 3 และ 4 |

| 7 | นำเข้าจาก Excel | L | 2 | ใช้การตรวจข้อมูลผู้ใช้ชุดเดียวกับโมดูล 2 |

## 0. โครงพื้นที่แอดมิน (ทำแล้ว 27 พ.ย. 2569)

- เพิ่มเมนูใน `app/utils/navigation.ts` ตามแบบ 7 รายการ เส้นทางขึ้นต้นด้วย `/admin`
  (ตั้งค่าบัญชีใช้ `/settings` เดิม)
- เปลี่ยน `homePathFor('admin')` จาก `/settings` เป็น `/admin`
- layout: `app/layouts/staff.vue` ใช้ร่วมกันระหว่างพี่เลี้ยงและแอดมิน หน้าที่หลายบทบาทใช้เลือกด้วย `layoutFor`
- หน้าที่ยังไม่ได้ทำใช้ `AdminPlaceholder` ลบคอมโพเนนต์นี้เมื่อทำครบทุกโมดูล
- เพิ่มบัญชีแอดมินทดสอบใน `mockData.ts` และ `mockAccounts.ts` และปุ่มเข้าบัญชีทดสอบในหน้าเข้าสู่ระบบ
- `app/types/admin.ts` และ `app/services/mockAdmin.ts` ย้ายไปสร้างในโมดูล 1 ซึ่งเป็นโมดูลแรกที่มีข้อมูล
  ให้โหลดแยกเหมือนข้อมูลจำลองอื่น
- ส่วนประกอบที่ใช้ซ้ำหลายหน้าในแบบ แยกเป็นคอมโพเนนต์ตั้งแต่ต้น

| คอมโพเนนต์ | ใช้ที่ |
|---|---|
| `FilterChips` แถบตัวกรองพร้อมจำนวน (ตัวที่เลือกขอบ primary) | ผู้ใช้งาน, การฝึกงาน, พี่เลี้ยงไม่อยู่ |
| `SelectField` ช่องเลือกที่มีป้ายชื่อและข้อความผิดพลาด | การฝึกงาน, พี่เลี้ยงไม่อยู่, อนุมัติแทน, ผู้ใช้งาน |
| `TablePagination` | ผู้ใช้งาน, การฝึกงาน |

เสร็จเมื่อ: เข้าบัญชีแอดมินแล้วเห็นเมนูครบ หน้า `/admin/*` ที่ยังไม่ทำแสดงว่างได้
บทบาทอื่นเปิด `/admin/*` แล้วไปหน้า `forbidden`

## 1. ตั้งค่าระบบ `/admin/settings` (ทำแล้ว 27 พ.ย. 2569)

| Method | Path | ใช้ |
|---|---|---|
| GET | `/admin/settings` | `{ backdateLimitDays, reviewOverdueDays, maxFailedLogins, lockMinutes, updatedAt, updatedBy }` |
| PUT | `/admin/settings` | `{ backdateLimitDays, reviewOverdueDays }` |

- แก้ได้สองค่า อีกสองค่าแสดงอย่างเดียว
- ตรวจเป็นจำนวนเต็ม 1–30
- ข้อมูลจำลอง: เปลี่ยน `BACKDATE_LIMIT_DAYS` และ `REVIEW_OVERDUE_DAYS` เป็นค่าที่แก้ได้ ทุกที่ที่ใช้ต้องอ่านค่าล่าสุด
- ตรวจหลังแก้: ฟอร์มบันทึกย้อนหลังเลือกวันได้ตามค่าใหม่ และป้ายค้างตรวจของพี่เลี้ยงเปลี่ยนตาม

## 2. ผู้ใช้งาน `/admin/users` (ทำแล้ว 27 พ.ย. 2569)

ต่างจากแผนเดิมตอนทำจริง

- หน้าตั้งรหัสครั้งแรกมีช่องรหัสผ่านปัจจุบันด้วย เพราะใช้ `/auth/change-password` ซึ่งต้องส่งรหัสเดิม
- บทบาทเปลี่ยนไม่ได้หลังสร้างบัญชี (**ข้อสมมติ** รอยืนยัน)
- ปุ่ม "นำเข้าจาก Excel" ตามแบบจะใส่ในโมดูล 7
- ข้อมูลจำลองมีบันทึกงานของนักศึกษาและพี่เลี้ยงตัวอย่างอย่างละคน บัญชีอื่นเข้าได้แต่หน้าข้อมูลแจ้งว่ายังไม่มีข้อมูล
  โมดูล 3 จะทำให้กำหนดข้อมูลฝึกงานและพี่เลี้ยงได้

| Method | Path | ใช้ |
|---|---|---|
| GET | `/admin/users?role=&status=&q=&page=` | รายชื่อ จำนวนตามบทบาท และจำนวนทั้งหมด |
| POST | `/admin/users` | เพิ่มผู้ใช้ `{ firstName, lastName, email, role, studentId? }` |
| PATCH | `/admin/users/:id` | แก้ข้อมูล หรือ `{ suspended: true \| false }` |
| POST | `/admin/users/:id/unlock` | ปลดล็อกก่อนครบเวลา |

- สถานะบัญชี: ใช้งาน, ล็อกถึงเวลา (จากการกรอกผิด), ระงับการใช้งาน
- อีเมลและรหัสนักศึกษาซ้ำไม่ได้ ตอบ 409 แสดงข้อความใต้ช่อง (4.3)
- ระงับบัญชีแล้ว session ของผู้นั้นถูกตัดทันที (4.1) ต้องยืนยันในหน้าต่างก่อนระงับ
- แอดมินระงับบัญชีตัวเองไม่ได้
- ฟอร์มเพิ่มและแก้ผู้ใช้**ยังไม่มีในแบบ** ใช้หน้าต่างตามรูปแบบหน้าต่างยืนยันใน design pattern
- รหัสผ่านเริ่มต้น: นักศึกษาใช้รหัสนักศึกษาของตน พี่เลี้ยงและแอดมินตั้งรหัสเองผ่านลิงก์ในอีเมล
- ฟอร์มเพิ่มนักศึกษาต้องบอกว่ารหัสผ่านเริ่มต้นคือรหัสนักศึกษา และบังคับกรอกรหัสนักศึกษา
- backend เก็บรหัสผ่านเป็น hash เหมือนรหัสอื่น รหัสเริ่มต้นเดาได้ ดูหัวข้อ "ความเสี่ยงที่เหลือ"

### บังคับตั้งรหัสผ่านใหม่เมื่อเข้าสู่ระบบครั้งแรก

ใช้กับนักศึกษาที่ยังใช้รหัสผ่านเริ่มต้น (บทบาทอื่นตั้งรหัสเองจากลิงก์อยู่แล้ว)

- `UserProfile` เพิ่ม `mustChangePassword` เป็นจริงเมื่อสร้างหรือนำเข้านักศึกษา
- หน้าใหม่ `/first-password` ใช้ layout เดียวกับหน้าเข้าสู่ระบบ **ยังไม่มีในแบบ Figma**
  กรอกรหัสผ่านใหม่และยืนยัน และมีปุ่มออกจากระบบ
- `auth.global.ts`: ถ้า `mustChangePassword` เป็นจริง ทุกหน้าที่ต้องเข้าสู่ระบบพาไป `/first-password`
  เมื่อเปลี่ยนแล้วไปหน้าแรกของบทบาท หรือหน้าที่ตั้งใจจะเปิด
- ใช้ `POST /auth/change-password` เดิม สำเร็จแล้วเซิร์ฟเวอร์ตั้ง `mustChangePassword` เป็นเท็จ
  การตั้งรหัสผ่านใหม่ผ่านลิงก์ทางอีเมลก็ล้างค่านี้ด้วย
- รหัสใหม่อย่างน้อย 8 ตัวอักษร ห้ามตรงกับรหัสเดิมหรือรหัสนักศึกษา
- backend ต้องปฏิเสธ endpoint ข้อมูลทุกตัวด้วย 403 `code: password_change_required` จนกว่าจะเปลี่ยน
  อนุญาตเฉพาะ `/me`, `/auth/change-password` และ `/auth/logout`
- ข้อมูลจำลอง: เพิ่มบัญชีนักศึกษาที่ยังไม่เคยเข้าใช้หนึ่งบัญชีไว้ทดสอบ
- ตรวจ: พิมพ์ URL หน้าอื่นหรือรีเฟรชระหว่างยังไม่เปลี่ยน ต้องกลับมาหน้านี้

## 3. การฝึกงานและพี่เลี้ยง `/admin/internships` (ทำแล้ว 27 พ.ย. 2569)

ต่างจากแผนเดิมตอนทำจริง

- จอแคบกว่า **1280px** (เดิมกำหนด 1024px) แผงแก้ไขเปิดเป็นหน้าต่างกลางจอ ไม่ใช่เต็มจอ
  เพราะที่ 1024–1279px ตารางไม่มีที่พอเมื่อมีแผงด้านข้าง
- มีการแก้ที่ยังไม่บันทึก เลือกนักศึกษาคนอื่นหรือกด Escape ไม่ทิ้งข้อมูล ต้องกดบันทึกหรือยกเลิกก่อน
- ภาคการศึกษาของข้อมูลฝึกงานใหม่ใช้ค่าคงที่ ฟอร์มยังไม่มีช่องกรอก
- ข้อมูลจำลองเปลี่ยนเป็นหนึ่งระเบียนต่อนักศึกษา ทุกบัญชีจึงเห็นข้อมูลของตัวเอง

| Method | Path | ใช้ |
|---|---|---|
| GET | `/admin/internships?filter=all\|no_mentor\|no_hours&q=` | ตารางด้านซ้าย |
| GET | `/admin/internships/:studentId` | แผงแก้ไข พร้อมประวัติพี่เลี้ยง |
| PUT | `/admin/internships/:studentId` | `{ company, position, startDate, endDate, workStartTime, workEndTime, mentorId }` |

- เลือกแถวแล้วแผงด้านขวาแสดงข้อมูล จอแคบกว่า 1024px แผงเปิดเป็นหน้าต่างเต็มจอแทน
- ตรวจ: วันสิ้นสุดหลังวันเริ่ม เวลาเลิกงานหลังเวลาเข้างาน
- เปลี่ยนพี่เลี้ยง: เก็บประวัติคนเดิมและวันที่เปลี่ยน (ตาราง `mentor_assignments`) งานรอตรวจย้ายไปพี่เลี้ยงคนใหม่
- เปลี่ยนเวลางาน: รายการเดิมตรวจตามเวลางาน ณ วันที่ทำงาน เวลาใหม่มีผลตั้งแต่วันที่บันทึก
  ต้องเก็บเวลางานพร้อมวันเริ่มมีผล และให้การตรวจเวลาในฟอร์มบันทึกงานอ่านตามวันที่ของรายการ
  ข้อความเตือนในแบบ Figma เปลี่ยนเป็นบอกว่ารายการเดิมไม่เปลี่ยน
- ข้อมูลจำลอง: ทำให้ `internship` และ `otherStudents` แก้ได้ หน้าข้อมูลสถานที่ฝึกงานของนักศึกษาต้องเห็นค่าใหม่

## 4. พี่เลี้ยงไม่อยู่ `/admin/mentor-absences` (ทำแล้ว 27 พ.ย. 2569)

ต่างจากแผนเดิมหรือกำหนดเพิ่มตอนทำจริง

- ฟอร์มกับตารางอยู่ข้างกันเมื่อจอกว้างตั้งแต่ **1280px** แคบกว่านั้นเรียงบนลงล่าง
- ห้ามซ้อนเฉพาะช่วง**ประเภทเดียวกัน** แอดมินบันทึก "ไม่อยู่" ทับช่วง "ไม่สะดวกตรวจ" ที่พี่เลี้ยงแจ้งไว้ได้ ตามแบบ
- บันทึกได้เฉพาะช่วงที่ยังไม่สิ้นสุด (**ข้อสมมติ** รอยืนยัน) เวลาเริ่มย้อนหลังได้
- ช่วงที่กำหนดไว้แต่ยังไม่เริ่ม ถ้าบันทึกผิดหรือยกเลิก **ลบไม่ได้** ปรับได้เฉพาะเวลาสิ้นสุดซึ่งต้องหลังเวลาเริ่ม (รอตัดสินใจ)
- นักศึกษาเห็นวันละหนึ่งช่วง ช่วงที่ยังไม่สิ้นสุดก่อน แล้ว "ไม่อยู่" ก่อน "ไม่สะดวกตรวจ" และไม่เห็นเหตุผล
- จำนวนการอนุมัติแทนเป็น 0 จนกว่าจะทำโมดูล 5 ซึ่งต้องห้ามปรับเวลาสิ้นสุดให้ก่อนเวลาที่อนุมัติแทนไปแล้วด้วย

| Method | Path | ใช้ |
|---|---|---|
| GET | `/admin/mentor-absences?type=all\|absent\|unavailable` | ทั้งช่วงที่แอดมินบันทึกและที่พี่เลี้ยงแจ้ง |
| POST | `/admin/mentor-absences` | `{ mentorId, startAt, endAt, reason }` ประเภท `absent` เสมอ |
| PATCH | `/admin/mentor-absences/:id` | `{ endAt }` ปรับเวลาสิ้นสุดเท่านั้น |

- ไม่มีปุ่มลบ พี่เลี้ยงกลับก่อนกำหนดให้ปรับเวลาสิ้นสุด (กติกาข้อ 4)
- ช่วงที่พี่เลี้ยงแจ้งเอง (`unavailable`) แสดงอย่างเดียว ปรับไม่ได้
- สถานะคำนวณจากเวลาเซิร์ฟเวอร์: ไม่อยู่ตอนนี้, กำหนดไว้, สิ้นสุดแล้ว
- ห้ามช่วงซ้อนกันของพี่เลี้ยงคนเดียว ห้ามเวลาสิ้นสุดก่อนเวลาเริ่ม
- ช่วงที่สิ้นสุดแล้วแสดงจำนวนงานที่อนุมัติแทนในช่วงนั้น
- ข้อมูลจำลอง: `absences` (แทน `unavailabilities` เดิม) มี `type`, `mentor`, `createdBy` หน้า "ตารางเวลาไม่สะดวก" ของพี่เลี้ยงใช้ข้อมูลเดียวกัน

## 5. อนุมัติแทน `/admin/proxy-reviews`

| Method | Path | ใช้ |
|---|---|---|
| GET | `/admin/proxy-reviews?mentorId=` | ช่วงไม่อยู่ปัจจุบัน และงานรอตรวจของนักศึกษาในความดูแล |
| POST | `/admin/proxy-reviews/approve` | `{ mentorId, items: [{ id, version }], comment? }` คืน `ReviewResult` |

- ใช้ `ReviewQueueList` และ `ReviewWorklogModal` ของพี่เลี้ยงซ้ำ โดยซ่อนการส่งกลับแก้ไข
- ไม่มีช่วงไม่อยู่ในขณะนี้: แสดงหน้าว่างพร้อมลิงก์ไปหน้าพี่เลี้ยงไม่อยู่
- ช่วงหมดระหว่างเปิดหน้า: เซิร์ฟเวอร์ตอบ 403 หน้าจอแสดงกล่องข้อผิดพลาดค้างไว้และโหลดคิวใหม่
- บันทึกว่าแอดมินอนุมัติแทนใครและอ้างอิงช่วงใด (`work_list_reviews.is_proxy`, `mentor_busy_id`)
  ประวัติรายการแสดงเป็น "อรุณี ศรีสุข อนุมัติแทน วิชัย พัฒนาการ"
- แจ้งเตือนนักศึกษาว่าอนุมัติแล้วเหมือนพี่เลี้ยงอนุมัติ

| Method | Path | ใช้ |

| GET | `/admin/overview` | ตัวเลข 4 ค่า รายการงานที่ต้องจัดการ ช่วงไม่อยู่ที่ใกล้ถึง และผลนำเข้าล่าสุด |

- งานที่ต้องจัดการคำนวณที่เซิร์ฟเวอร์ เรียงตามความเร่งด่วนในแบบ ปุ่มแต่ละรายการพาไปหน้านั้นพร้อมตัวกรอง
- ไม่มีงานค้าง: แสดงข้อความว่าไม่มีเรื่องที่ต้องจัดการ
- ปุ่มกระดิ่งแสดงที่หน้านี้ แจ้งแอดมิน 2 เรื่อง: พี่เลี้ยงไม่อยู่และมีงานรอตรวจ, นักศึกษายังไม่มีพี่เลี้ยง
  ใช้ endpoint `/notifications` เดิม เพิ่มชนิดใน `NotificationType`

## 7. นำเข้าจาก Excel (หน้าต่างในหน้าผู้ใช้งาน)

| Method | Path | ใช้ |
|---|---|---|
| POST | `/admin/imports/users/preview` | อัปโหลดไฟล์ คืนผลตรวจรายแถวและ `importId` |
| POST | `/admin/imports/users/:importId/commit` | นำเข้าเฉพาะแถวที่ผ่าน |
| GET | `/admin/imports/users/template` | ดาวน์โหลดแบบฟอร์ม |

- อ่านไฟล์ที่เซิร์ฟเวอร์ หน้าจอไม่แปลง Excel เอง
- คอลัมน์ในแบบฟอร์ม: ชื่อ, นามสกุล, อีเมล, บทบาท, รหัสนักศึกษา (บังคับเฉพาะนักศึกษา)
- ผลตรวจที่แบบแสดง: อีเมลซ้ำ ไม่มีรหัสนักศึกษา และพร้อมนำเข้า เรียงแถวที่ผิดก่อน
- ตรวจเพิ่ม: รหัสนักศึกษาซ้ำ บทบาทไม่ถูกต้อง และข้อมูลซ้ำกันภายในไฟล์
- ไม่เขียนทับบัญชีที่มีอยู่ แถวที่อีเมลซ้ำขึ้นข้อผิดพลาดและถูกข้าม ชื่อที่ผู้ใช้แก้เองจึงไม่เปลี่ยน
- นักศึกษาที่นำเข้าใช้รหัสนักศึกษาเป็นรหัสผ่านเริ่มต้น และต้องตั้งรหัสใหม่เมื่อเข้าครั้งแรก เหมือนโมดูล 2

## งานร่วมทุกโมดูล

- จอแคบ: แบบมีเฉพาะจอ 1440px ใช้รูปแบบเดิมของแอป ตารางเลื่อนในกรอบของตัวเอง เมนูเปลี่ยนเป็นแถบบน
- อัปเดต `docs/api-contract.md` ทีละโมดูล และลบหัวข้อออกจากส่วน "ยังไม่มีในสัญญานี้"
- อัปเดต `PRODUCT.md` เมื่อแต่ละโมดูลเสร็จ
- ตรวจก่อน commit ทุกโมดูล: `eslint`, `nuxt build`, คลิกผ่านทุกปุ่มด้วยบัญชีแอดมิน และเปิดหน้าด้วยบัญชีอื่นต้องเข้าไม่ได้
- backend ต้องตรวจสิทธิ์แอดมินทุก endpoint `/admin/*` เอง

## ความเสี่ยงที่เหลือ

การบังคับตั้งรหัสใหม่ปิดช่องได้เฉพาะบัญชีที่เจ้าของเข้าใช้ครั้งแรกแล้ว บัญชีที่**ยังไม่เคยเข้าใช้**
คนที่รู้อีเมลกับรหัสนักศึกษายังเข้าก่อนเจ้าของแล้วตั้งรหัสใหม่ได้

- หน้าผู้ใช้งานแสดง "ยังไม่เคยเข้าใช้" อยู่แล้ว แอดมินใช้ติดตามบัญชีเหล่านี้ได้
- ถ้าเจ้าของเข้าไม่ได้ ให้ตั้งรหัสผ่านใหม่จากลิงก์ทางอีเมล (`/forgot-password`) ซึ่งตัด session อื่นทั้งหมด
- ถ้าต้องปิดช่องนี้ ต้องใช้รหัสเริ่มต้นแบบสุ่มหรือลิงก์ทางอีเมลแทนรหัสนักศึกษา
